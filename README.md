## 2. 背景与目标

销售／运营既会选用已有 AI 生图，也会在外部工具中制作图片后本地上传。原有流程对图片来源、实际使用位置和后续更新的记录不完整。

A+ 的典型问题是：任务 A 有 3 张审核通过，任务 B 有 4 张审核通过，业务希望合成一套内容；据原交接反馈，逐任务推送会使后一次内容覆盖前一次，无法直接累计。这里记录的是业务反馈，具体覆盖行为仍需检查下游实际接口。

因此，生图任务负责生产素材，独立推送任务负责保存本次最终图片组合、顺序和处理结果。业务全程在新页面操作，Listing 与 A+ 下游系统负责相应平台接口转发和结果回传。

| 本地上传门槛 | 检测通过后，由本人直接确认推送，不增加一轮额外人工审核 |
| 业务闭环 | 在新页面完成选图、检测、组稿、预览、提交、查看结果及后续维护，无须进入下游页面操作 |

“仅做增量”指新产生的推送业务，不是只能选择新 ASIN 或刚生成的图片。已有店铺＋ASIN、已有审核通过 AI 图片仍可作为新推送的目标与素材。旧线上内容初始化、历史使用关系恢复和批量整改不因此自动纳入首版。

商品图与 A+ 都在整体项目范围内。先细化 A+ 是推进顺序，不代表取消商品图。

## 4. A+ 页面主线

### 4.1 推送列表

**一行代表一次独立 A+ 推送，同一店铺＋ASIN 可以有多行。** 已比较过以商品为一行的方案，当前采用推送任务列表，便于统一查看人工、自动推送及各次结果，保留完整历史。

原型展示店铺／ASIN、图片数量、推送单号、任务来源、发起人、状态、时间和详情入口；支持店铺、ASIN、状态、任务来源筛选。具体字段与筛选组合仍可随评审调整。

列表保留“新建 A+ 推送”入口，使有素材但尚无推送记录的商品也能开始组稿。权限如何决定可选目标，见第 6 节。

### 4.2 人工新建

选择店铺＋ASIN → 查询可用 AI 图片／本地上传并检测 → 选入本次发布内容 → 调整顺序 → 预览确认 → 生成独立推送记录 → 跟踪结果。

- 左侧是可选素材，AI 图片按来源任务分组；右侧是本次最终图片及顺序。
- 同一店铺＋ASIN 可跨任务选图，由业务决定组合；本地检测通过图片也可加入。
- 素材展示顺序与最终发布顺序是两回事，下游使用的是最终选定顺序。
- A+ 不增加模板和文字输入。**图片数量、尺寸、格式、重复图片规则尚未确定。**
- 当前原型不保存草稿。首版是否需要草稿仍是待确认项，不能从原型没有按钮推导出最终规则。

### 4.3 自动推送

保留原交接中单个完整生图任务审核通过后自动推送的方向，不让业务额外手工确认一遍。自动与人工推送都应形成独立任务和完整快照，进入同一列表。

原交接明确的已有场景为“单任务 7 张全部审核通过”。这不是所有 A+ 必须恰好 7 张的通用规则，其他数量与完整性判定需核实。

单任务仅部分图片通过时保留为可用素材，不直接按残缺图片集合推送。任务 A 的 3 张和任务 B 的 4 张，即使累计到 7 张，也不自动跨任务凑图发布，由业务人工选图排序。

### 4.4 详情与后续修改

每次提交保存具体图片版本、顺序、来源、目标及发起信息，原提交快照保持不变。调整图片组合后形成新推送，保留前次记录；查询结果仍关联原推送任务。

原型提供“基于这次内容修改”；处理中暂禁用该操作，只是当前演示处理。处理中能否新建替代版本、同一目标能否并发提交及如何避免旧任务覆盖新结果，仍需确认。

“修改后新推送”与“原提交发生通信异常后重试”不同。异常重试是否复用原任务 ID，必须结合幂等能力确认。

## 5. 推送与下游系统的边界

当前承接原交接中的接口约定：我方生成独立 A+ 推送 `taskId`，通过接口 1 提交，再用同一个 `taskId` 调用接口 2 查询最终结果。推送 ID 与生图任务 ID 分开；一次组稿可追溯多个生图任务。

**上述是交接约定，尚未核验实际接口文档、请求响应或联调结果。** 不预设接口路径、字段、轮询频率和重试次数。

发布必须能关联：来源图片及版本 → 店铺＋ASIN → A+ 图片位置／商品图槽位 → 本次推送 → 下游与平台结果。URL 只是文件地址，不能替代完整关系。

接口接收成功不等于平台处理成功，更不能直接声称亚马逊前台已展示。原型中的“处理中／上传成功／上传失败”都是示例状态，真实名称与成功含义以实际可取得的回执为准；超时、查不到任务或结果未知不能直接当成已失败并重复提交。

## 6. 权限：现状、继承方案与新增建议

**这一节仍需结合新页面范围确认，原型没有实现权限控制。**

原交接记录的现状：没有可靠的用户→店铺→ASIN 权限映射；AI 生图可选择所有店铺。已有生图任务查看范围是普通用户看自己，组长看自己＋组员，管理员看全部。以上是业务交接信息，当前系统实际配置尚未复核。

原 A+ 方案采用两层控制：先用“可见的已完成标普 A+ 任务”确定店铺＋ASIN 准入；进入获准商品后，可复用该店铺＋ASIN 下已完成任务中审核通过的标普 A+ 图片，不再按创建人限制素材。这不代表所有人可浏览所有商品素材。

新增本地上传后，讨论中的建议是：

| 对象 | 建议方案，待确认 |
|---|---|
| 功能与本地上传准入 | 已获功能权限的用户可选择有效店铺＋ASIN，新建本地上传推送，不强制先有 AI 生图任务 |
| AI 图片复用 | 继续按原两层方案确定 AI 素材准入；仅本地上传不自动开放他人的 AI 图片 |
| 推送记录查看 | 普通用户看自己，组长看自己＋组员，管理员看全部 |
| 推送归属 | 人工推送归确认人；自动推送归来源生图任务创建人 |
| 本地图片复用 | 先通过可见推送记录复用，不默认建立所有人共享的本地上传素材池 |

该建议可以降低首版建设成本，但还不能证明用户拥有目标 ASIN 的发布权，也可能使同一 ASIN 的同事看不到彼此推送。需要业务与研发确认可接受范围及同目标操作提示，不能把建议写成已落地的权限保障。

## 7. 接下来分批确认的问题

先围绕页面交流，一次讨论一个主题，不要求业务一次回答全部接口问题。

| 顺序 | 主题 | 待确认内容 | 主要确认方 |
|---|---|---|---|
| 1 | A+ 图片与组稿 | 最少／最多／固定数量；格式、尺寸、大小；是否允许重复图；是否需要草稿 | 业务＋研发 |
| 2 | 新功能权限 | 第 6 节建议能否接受；目标准入、AI 素材、推送记录可见范围 | 业务＋研发 |
| 3 | 下游最小闭环 | 有序图片能否直接提交；实际状态与成功含义；同 ID 幂等、任务查不到、超时和失败后的处理 | 下游研发 |
| 4 | 检测与版本 | 外部真实照片／外部 AI／混合图适用哪些检测；结果复用、必要打标与发布文件版本 | 检测及存储研发 |
| 5 | 更新与冲突 | 同一目标并发／连续推送、旧任务晚返回、平台已有内容替换范围、内容是否共享多个 ASIN | 业务＋下游研发 |

即使首版不迁移存量，新推送对既有线上内容的影响范围仍需在真实上线前明确。

商品图留待 A+ 主线稳定后继续：用户说明下游 Listing 按店铺＋MSKU 工作，AI 生图和 A+ 按店铺＋ASIN 工作。常见多 MSKU 场景是 FBA／FBM 并存；其他可能场景（如 PanEU、二手）尚待业务核实。是否让用户选 MSKU、一次更新一条还是多条均未定，**该问题已主动搁置**。

## 8. 当前原型能做什么

`index.html` 是完整静态 HTML，样式和脚本都在文件内，不依赖安装环境、外部图片、在线服务或对话内展示运行器。

| 已有示例交互 | 当前限制 |
|---|---|
| A+ 列表及条件筛选 | 固定示例店铺、ASIN、发起人和状态；无真实权限或数据查询 |
| 跨 AI 任务选图、移除、拖拽／上下排序 | 使用 A1、B1 等占位图片；没有访问真实素材 |
| 本地上传区域 | 按钮只是添加“检测通过”的示例图片，没有读取本地文件或调用检测 |
| 预览并确认推送 | 只在浏览器内增加一条“处理中”示例记录，不会发出发布请求 |
| 快照详情、基于历史内容修改 | 来源与 v1 为演示信息，没有真实版本存储或更新接口 |
| 切换 ASIN 清空选中内容并切换素材 | 只是两个示例 ASIN 的前端隔离，不等于后端权限验证 |

**刷新页面会恢复初始示例。页面中的选图、示例记录不会保存到 GitHub，也不会随着仓库同步到另一台电脑。** GitHub 同步的是 HTML 源码、需求文档等已提交文件。

商品图 Tab 当前不可点击；这只是尚未绘制。数量为空时禁止预览是演示防误操作，选一张能继续并不代表真实发布最低数量已确定。

### 预览与轻量检查

直接用 Chrome 打开本地 `index.html`，或访问顶部 Pages 链接。当前无须运行安装、构建或服务器命令。

调整原型后检查：

1. 列表筛选、新建入口与返回路径正常；未选图片时不能预览。
2. 同一 ASIN 可跨任务选图并调整顺序；预览与详情顺序一致。
3. 添加本地示例后可参与组稿；模拟确认生成新记录，旧记录保持原组合。
4. 切换 ASIN 后不残留其他 ASIN 的选图或本地示例；自动推送示例只来自一个完整任务。
5. Chrome 无脚本错误，窄屏无横向溢出；线上发布后重新检查关键操作。

这验证的是原型交互，不代表检测、文件保存、下游或亚马逊业务链路通过验收。

## 9. 两台电脑如何轮流继续

推荐把 GitHub 仓库作为文件同步位置。两台电脑的本地目录可以不同，链接和说明应尽量使用仓库相对路径。

### 家里的电脑首次使用

1. 安装并登录 GitHub Desktop（或使用已配置好的 Git），克隆 `https://github.com/xuqiang97/amazon-asin-image-hub.git`。
2. 在 Codex 中打开克隆下来的项目文件夹，开始新任务，让助手先读 `AGENTS.md` 和 `README.md`。
3. 用 Chrome 打开该文件夹的 `index.html`，结合页面继续讨论。

### 每次切换电脑

| 时机 | 操作 |
|---|---|
| 开始前 | 先确认本机没有未处理改动，再获取并拉取 GitHub 最新进度（GitHub Desktop：Fetch origin／Pull origin） |
| 工作中 | 修改原型后同步更新 README 中相关结论；区分已确认、建议和待核实事项 |
| 离开前 | 检查变更、提交，并推送 GitHub（Commit／Push origin）；确认推送成功 |
| 换另一台 | 先拉取，再继续；避免两台电脑同时各自修改同一份文件 |

仅“提交”还没有上传到 GitHub，必须完成“推送”。若另一台电脑有未提交改动或两边已经分叉，先保留改动并查看差异，解决冲突后再同步；不要强行覆盖或强推来清除进度。

熟悉命令行时，可在仓库目录使用：

```sh
# 每次开始：先看本机状态，再拉取
git status
git pull --ff-only

# 收工：检查差异后，只添加本次确认要同步的文件
git diff
git add README.md AGENTS.md index.html
git diff --cached --check
git commit -m "说明本次更新内容"
git push origin main
```

新增文件需按实际路径加入提交，例子中的文件列表不是自动同步全部文件。`pull --ff-only` 不能快进时停下来处理差异，不使用强推或丢弃改动绕过。

对话记录、本机长期记忆、登录凭据、插件和本机工具不会随 Git 仓库一起同步。延续项目依靠本文中的业务结论与 `AGENTS.md` 中的规则；两台电脑分别配置必要工具即可。克隆后可以用这句话接续：

> 请先阅读 AGENTS.md 和 README.md，查看 index.html。我们从 README 的下一步继续讨论 A+ 页面，区分已确认与待确认事项，先不要自行改文件或发布。

本仓库是公开的。推送会公开相应文件，并触发 `main` 根目录的 Pages 部署；只加入明确要共享的项目资料，不提交凭据、真实业务数据或本机缓存。
